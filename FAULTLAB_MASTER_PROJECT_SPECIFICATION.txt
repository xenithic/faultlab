============================================================
1. PROJECT OVERVIEW
============================================================

FaultLab is a web-based chaos engineering and resilience testing
platform for containerized applications.

The platform allows users to intentionally introduce controlled
failures into an isolated target application, observe the resulting
system behavior, collect performance and infrastructure metrics,
measure recovery, and compare resilience before and after
improvements.

The core engineering workflow is:

INJECT → OBSERVE → MEASURE → RECOVER → COMPARE

FaultLab is designed as an educational/research-oriented resilience
testing platform rather than a replacement for enterprise chaos
engineering products.

============================================================
2. PROBLEM STATEMENT
============================================================

Modern applications increasingly rely on multiple interconnected
services. Failures in one service, database, network connection, or
infrastructure component can cause performance degradation,
cascading failures, or complete service disruption.

Traditional testing often focuses on whether an application works
under normal conditions. It may not adequately reveal how the
application behaves when dependencies fail or resources become
constrained.

FaultLab addresses this problem by providing a controlled environment
where failures can be deliberately introduced into containerized
applications and their effects can be measured.

Instead of waiting for real-world failures to reveal weaknesses,
developers can perform controlled resilience experiments and use the
results to identify areas for improvement.

============================================================
3. PRIMARY OBJECTIVE
============================================================

The primary objective of FaultLab is to provide a safe, controlled,
and measurable environment for testing the resilience of
containerized applications.

The platform should allow a user to:

1. Select a registered target application/service.
2. Select a controlled fault type.
3. Configure fault parameters such as duration or intensity.
4. Establish/record a baseline.
5. Inject the selected fault.
6. Monitor the application's behavior during the experiment.
7. Observe recovery after the fault ends or is removed.
8. Calculate and store experiment results.
9. Compare results across experiments.
10. Use the results to evaluate resilience improvements.

============================================================
7. FAULTLAB CORE FAULT TYPES
============================================================

The initial core scope contains FIVE fault categories.

------------------------------------------------------------
7.1 SERVICE FAILURE
------------------------------------------------------------

A selected target container/service is intentionally stopped.

Example:

Order Service
    ↓
FAULT
    ↓
Order Service DOWN

Implementation may use the Docker SDK to control the registered
target container.

------------------------------------------------------------
7.2 SERVICE PAUSE / RESTART
------------------------------------------------------------

A service can be temporarily interrupted and subsequently restarted.

Purpose:

- Observe temporary service disruption.
- Measure recovery behavior.

------------------------------------------------------------
7.3 LATENCY INJECTION
------------------------------------------------------------

Controlled delay is introduced into service communication or request
processing.

Example:

Normal latency: 40 ms
Injected latency: 500 ms

Purpose:

- Study application behavior under slow dependencies.
- Observe latency propagation.
- Evaluate timeout/fallback behavior where applicable.

------------------------------------------------------------
7.4 CPU / MEMORY RESOURCE STRESS
------------------------------------------------------------

Controlled CPU or memory pressure is introduced against a registered
target container.

Purpose:

- Observe performance degradation.
- Monitor resource utilization.
- Evaluate application behavior under resource constraints.

------------------------------------------------------------
7.5 HTTP ERROR INJECTION
------------------------------------------------------------

Controlled HTTP failures can be introduced.

Examples:

- HTTP 500
- HTTP 503

The fault may be configured to affect a percentage of requests.

Purpose:

- Study application behavior under dependency/API errors.
- Observe error propagation and graceful failure.

============================================================
8. FAULT INJECTION BOUNDARY
============================================================

FaultLab must operate only on explicitly registered and isolated
target environments.

FaultLab must NOT be designed to attack arbitrary external systems.

Fault injection should be restricted to the project's controlled
Docker environment.

This provides:

- Safety
- Isolation
- Reproducibility
- Controlled experimentation

The platform should validate that a requested experiment targets a
registered FaultLab environment/container.

2. Select target

12. RESILIENCE EVALUATION
============================================================

FaultLab is not simply a tool for stopping containers.

The purpose is to evaluate how well an application behaves under
controlled failures.

The general engineering cycle is:

Normal System
      ↓
Controlled Failure
      ↓
Observe Impact
      ↓
Measure
      ↓
Identify Weakness
      ↓
Improve Application
      ↓
Repeat Experiment
      ↓
Compare Results

Example:

BEFORE RESILIENCE IMPROVEMENT:

Error Rate: 38%
Recovery Time: 14.2 sec
Availability: 71%

AFTER adding an appropriate resilience mechanism:

Error Rate: 7%
Recovery Time: 3.1 sec
Availability: 94%

The values are illustrative.

The actual project should use measured experimental data.

Possible resilience mechanisms that may be demonstrated include:

- Timeouts
- Retry limits
- Circuit breakers
- Graceful degradation
- Redundancy/failover

These mechanisms are primarily part of the TARGET APPLICATION /
experimental evaluation rather than separate FaultLab core features.

24. SAFETY
============================================================

FaultLab is intended for controlled experimentation.

Experiments must operate only on isolated, registered Docker-based
target environments.

The system should not provide functionality intended to disrupt
arbitrary external infrastructure.

Experiments should have controlled duration/intensity and should
include appropriate validation before execution.

============================================================
25. PROJECT TERMINOLOGY
============================================================

FaultLab:
The overall chaos engineering and resilience testing platform.

Target Application:
The containerized application being tested.

Experiment:
A controlled fault-injection session.

Fault:
The controlled failure/condition introduced during an experiment.

Baseline:
System behavior measured before fault injection.

Impact:
The observed degradation caused by the fault.

Recovery:
The process through which the target returns toward normal behavior.

Recovery Time:
The measured time required for the target to recover after the
fault is removed or the service is restored.

Resilience:
The ability of the application to continue operating acceptably
and recover when failures occur.

Fault Injection:
The deliberate introduction of a controlled failure into the
registered target environment.
